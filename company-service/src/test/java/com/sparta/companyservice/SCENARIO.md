# Company 통합 테스트 시나리오

이 문서는 `company-service`에서 수행되는 통합(Scenario) 테스트의 비즈니스 흐름을 사람의 언어로 정의합니다. 모든 테스트는 `IntegrationTestSupport`를 상속받아 수행됩니다.

## 🛠️ 공통 전제 조건
- **환경**: SpringBoot 기반 통합 테스트 (`@SpringBootTest`)
- **도구**: `MockMvc`를 사용하여 API 호출 및 검증
- **인증/인가**: Gateway에서 전달되는 `X-User-Id`, `X-User-Role` 헤더를 수동으로 주입하여 권한별 동작을 검증함.
- **데이터 정합성**: `@Transactional`을 통해 각 테스트 종료 후 데이터를 자동 롤백함.

---

## 📋 시나리오 리스트

### 1. 업체 관리 핵심 흐름 (등록 -> 수정 -> 조회)
이 시나리오는 업체가 시스템에 등록된 후, 관리자에 의해 정보가 변경되고, 사용자가 이를 조회하는 일련의 과정을 검증합니다.

- **Step 1: 업체 신규 등록**
    - **행동**: `MASTER` 권한 헤더를 포함하여 `POST /api/v1/companies` 호출. (사업자 번호, 이름, 타입 등 포함)
    - **기대 결과**: 응답 상태 코드 `201 Created`를 반환하고, 응답 데이터에 생성된 `companyId`가 포함되어야 함.
- **Step 2: 업체 정보 수정**
    - **행동**: `HUB_MANAGER` 권한 헤더를 포함하여 `PATCH /api/v1/companies/{companyId}` 호출. (업체 이름 또는 타입을 변경)
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환하고, 응답 데이터에 수정된 내용이 반영되어야 함.
- **Step 3: 최종 상태 조회 및 검증**
    - **행동**: `CUSTOMER` 권한 헤더를 포함하여 `GET /api/v1/companies/{companyId}` 호출.
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환하며, Step 2에서 수정한 정보가 정확히 조회되어야 함.

---

### 2. 상품 등록 및 상세 조회 흐름
이 시나리오는 새로운 상품이 등록된 후, 사용자가 상품의 상세 정보를 정확하게 조회할 수 있는지 검증합니다.

- **Step 1: 상품 신규 등록**
    - **행동**: `COMPANY_MANAGER` 또는 `MASTER` 권한 헤더를 포함하여 `POST /api/v1/products` 호출. (상품명, 가격, 설명, 업체 ID 등 포함)
    - **기대 결과**: 응답 상태 코드 `201 Created`를 반환하고, 응답 데이터에 생성된 `productId`가 포함되어야 함.
- **Step 2: 상품 상세 조회 및 검증**
    - **행동**: `ANY` 권한으로 `GET /api/v1/products/{productId}` 호출.
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환하며, Step 1에서 등록한 상품명과 가격 정보가 정확히 포함되어야 함.

### 3. 상품 판매 상태 변경 및 노출 제어 흐름
이 시나리오는 판매 중인 상품의 상태를 변경(예: 품절 또는 숨김)했을 때, 일반적인 상세 조회에서 제외되는지 검증합니다.

- **Step 1: 기존 상품의 판매 상태 변경**
    - **행동**: `COMPANY_MANAGER` 권한으로 `PATCH /api/v1/products/{productId}/status` 호출. (상태를 `OUT_OF_STOCK` 또는 `HIDDEN`으로 변경)
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환하고, 상태 변경이 완료되어야 함.
- **Step 2: 판매 중단 상품 상세 조회 시도**
    - **행동**: `CUSTOMER` 권한으로 `GET /api/v1/products/{productId}` 호출.
    - **기대 결과**: 비즈니스 정책에 따라 `404 Not Found`를 반환하거나, 응답 데이터의 `isPublic` 필드가 `false`임을 확인하여 조회 대상에서 제외되었음을 검증함.

### 4. 상품 옵션 생성 및 관리 흐름
이 시나리오는 상품에 종속된 다양한 옵션(사이즈, 색상 등)을 생성하고, 이를 상세 조회할 수 있는지 검증합니다.

- **Step 1: 상품 옵션 신규 생성**
    - **행동**: `COMPANY_MANAGER` 권한으로 `POST /api/v1/products/{productId}/options` 호출. (옵션명, 추가 금액 등 포함)
    - **기대 결과**: 응답 상태 코드 `201 Created`를 반환하고, 생성된 `optionId`가 응답에 포함되어야 함.
- **Step 2: 상품 옵션 상세 조회 및 정합성 검증**
    - **행동**: `GET /api/v1/product-options/{optionId}` 호출.
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환하며, Step 1에서 지정한 옵션 정보가 상품 정보와 연결되어 정확히 조회되어야 함.


### 5. 업체 삭제 및 소프트 딜리트(Soft Delete) 검증 흐름
이 시나리오는 업체를 삭제했을 때 데이터베이스에서 실제로 제거되지 않고 삭제 상태로 마킹(Soft Delete)되며, 일반 조회에서 제외되는지 검증합니다.

- **Step 1: 업체 삭제 요청**
    - **행동**: `MASTER` 권한으로 `DELETE /api/v1/companies/{companyId}` 호출.
    - **기대 결과**: 응답 상태 코드 `204 No Content` 또는 `200 OK`를 반환해야 함.
- **Step 2: 삭제된 업체 상세 조회 시도**
    - **행동**: `GET /api/v1/companies/{companyId}` 호출.
    - **기대 결과**: 응답 상태 코드 `404 Not Found`를 반환하여 일반적인 조회 경로에서는 접근이 불가능함을 확인.
- **Step 3: DB 상태 직접 검증 (Internal)**
    - **행동**: 리포지토리를 통해 해당 엔티티의 `isDeleted` 필드가 `true`인지 확인.
    - **기대 결과**: 데이터가 실제로 존재하며 삭제 마킹만 되어 있어야 함.

### 6. 업체 관리자(COMPANY_MANAGER)의 자기 업체 정보 수정 권한 검증
이 시나리오는 업체 관리자가 자신이 소속된 업체의 정보만 수정할 수 있고, 타 업체의 정보는 수정할 수 없는 보안 규칙을 검증합니다.

- **Step 1: 소속 업체 정보 수정**
    - **행동**: 본인이 관리하는 `companyId`에 대해 `PATCH /api/v1/companies/{companyId}` 호출.
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환하고 수정이 성공해야 함.
- **Step 2: 타 업체 정보 수정 시도**
    - **행동**: 다른 업체(`otherCompanyId`)에 대해 동일한 수정 API 호출.
    - **기대 결과**: 응답 상태 코드 `403 Forbidden`을 반환하여 접근이 거부되어야 함.

### 7. 배송지(Address) 등록 및 기본 배송지 설정 흐름
이 시나리오는 업체에서 사용할 배송지들을 등록하고, 그중 하나를 기본 배송지로 설정하는 과정을 검증합니다.

- **Step 1: 다건의 배송지 등록**
    - **행동**: `POST /api/v1/companies/{companyId}/addresses`를 반복 호출하여 여러 배송지 등록.
    - **기대 결과**: 각각 `201 Created`를 반환해야 함.
- **Step 2: 기본 배송지(Default Address) 설정**
    - **행동**: 특정 `addressId`를 지정하여 `PATCH /api/v1/companies/addresses/{addressId}/default` 호출.
    - **기대 결과**: 응답 상태 코드 `200 OK`를 반환.
- **Step 3: 기본 배송지 설정 정합성 확인**
    - **행동**: 업체 상세 조회 또는 배송지 목록 조회를 통해 해당 주소만 `isDefault`가 `true`이고 나머지는 `false`인지 확인.
    - **기대 결과**: 단 하나의 기본 배송지만 활성화되어 있어야 함.
