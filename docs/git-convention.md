# Git / GitHub 브랜치 및 커밋 컨벤션

이 문서는 팀의 버전 관리 규칙, 브랜치 전략, 네이밍 및 커밋 컨벤션을 정의한다.

---

## 1. 협업 규칙

- **브랜치 보호 및 강제 푸시 차단**: `develop` 브랜치 및 `main` 브랜치로의 직접적인 push는 금지하며, 강제 푸시(force push) 역시 엄격히 차단한다.
- **PR 기반 병합**: 모든 작업은 개인 브랜치에서 완료 후 PR(Pull Request)을 생성하여 병합을 진행한다.
- **코드 리뷰 필수 적용**: 생성된 PR은 최소 1명 이상의 팀원 승인(approve)을 거쳐야 `dev` 브랜치에 병합할 수 있다.
- **자동화 알림 연동**: 지속적 통합(CI) 및 개발 프로세스의 투명한 공유를 위해 병합 및 주요 이벤트 발생 시 Discord 알림을 통해 실시간으로 공유한다.

---

## 2. 브랜치 구조 및 유형

| 브랜치 | 역할 |
| :--- | :--- |
| `main` | 최종 배포용 브랜치. 제출 및 최종 완성본만 관리하며 직접 작업은 금지한다. |
| `dev` | 개발 통합 브랜치. 각 팀원의 작업 코드를 합쳐서 기능 통합 및 테스트를 수행하는 공간이다. |
| `dev/[이름]` | 개인 작업 브랜치. 각 팀원의 이름을 명시하여 독립적으로 기능을 개발하는 공간이다. |

**병합 방향**: `main` ← `dev` ← `dev/[이름]`

### 브랜치 생성 및 운영 유의사항

- 새로운 기능 구현이나 수정 작업이 필요한 경우, 최신 상태의 `dev` 브랜치에서 자신의 이름을 딴 개인 작업 브랜치(`dev/[이름]`)를 생성하여 진행한다.
- 개인 작업 브랜치에서 완료된 결과물은 절대 직접 푸시하지 않고, 반드시 Pull Request를 통해 `dev` 브랜치로 병합을 요청하여야 한다.

## 3. 커밋 및 Task 유형

| 유형 | 설명 |
| :--- | :--- |
| `feat` | 새로운 기능 추가 (예: API 구현 등) |
| `fix` | 버그 수정, 잘못된 로직 및 오류/예외 처리 수정 |
| `refactor` | 기능 변경 없는 코드 구조 개선 (가독성 향상, 중복 제거, 트랜잭션 분리 등) |
| `docs` | 문서 수정 (README.md, 내부 주석, 가이드 문서 등) |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 빌드 업무, 패키지 매니저 설정, 환경 설정 파일 변경 (예: application.yml 설정 등) |
| `style` | 코드 포맷팅, 세미콜론 누락 수정 등 기능에 영향을 주지 않는 스타일 변경 |

## 4. 네이밍 및 메시지 규칙

모든 네이밍과 식별자는 아래 규칙에 명시된 형식을 엄격히 준수하여 작성한다.

| 항목 | 형식 | 예시 |
| :--- | :--- | :--- |
| 브랜치 이름 | `dev/[작업자 이름]` | `dev/honggildong`, `dev/kimchulsoo`, `dev/leeyounghee` |
| Commit 메시지 | `[TASK 유형]: [작업내용요약]` | `feat: 메뉴 등록 API 구현`<br>`fix: 메뉴 숨김 처리 시 권한 오류 수정` |
| PR 제목 | Commit 메시지 명세와 동일하게 작성 | `refactor: MenuService 트랜잭션 분리`<br>`chore: application.yml 환경변수 설정 추가` |
